# 窗口指令、语音排队与按需看一眼（2026-11-07）

本次解决三件事：窗口操作为什么点不动、播报为什么自己打断自己、以及"给咕嘎长眼睛"该怎么落地。

## 一、窗口操作用系统命令，不做控件点击

### 结论

最大化、最小化、还原、关闭窗口不需要读无障碍树，也不需要截图。它是窗口状态，
直接走 Win32 `ShowWindow` / `WM_CLOSE`，用 `GetWindowPlacement` 的 showCmd 回读验证。

新增动作 `window_control`，在 `core/fast_commands.py`，与现有快速命令同一条本地通路，
不经过大模型。实测单次约 20 毫秒。

支持的说法包括：最大化、窗口最大化、最大化窗口、把窗口最大化、帮我把这个窗口最大化、
放到最大、铺满屏幕、放大窗口、最大化浏览器；最小化、最小化窗口、收到任务栏、最小化到任务栏；
还原窗口、恢复窗口、恢复窗口大小、恢复正常大小、取消最大化；关闭窗口、关掉当前窗口、
把这个窗口关掉。

`最大化浏览器` 这类会额外校验前台进程确实是浏览器，否则直接说明"当前前台不是浏览器"，
不会误操作别的窗口。桌面、任务栏、咕嘎自己的窗口都拒绝执行。

### 一个必须记住的细节

窗口最小化后，前台会自动切换到别的窗口。如果用户接着说"还原"，按当前前台执行就会还原错窗口。
因此新增窗口记忆：记住上一次操作过的窗口十秒，最小化状态下说"还原"优先作用于它。

### 关于 UIA 的一个更正

早期判断"浏览器标题栏按钮不在 UIA 树里"是**错的**，原因是探测时抓错了窗口句柄
（豆包进程下有一个标题为空的宿主窗口，其树只有四个节点）。实测真实的豆包浏览器窗口
（`Chrome_WidgetWin_1`，标题非空）可以读出完整控件树，最大化/最小化/关闭都是 `Button`
且支持 `InvokePattern`，读取耗时约 60 毫秒。

但 Chromium 的无障碍树是懒构建的，首次访问可能拿到骨架。`core/quick_look.py` 对
"元素过少"重试一次；对超时不重试，因为超时说明树太大，重试只会翻倍等待。

## 二、播报互相打断：客户端没有播放队列

### 根因

`_request_audio_response` 原先只检查服务端状态（`_generating`、`_response_id`），
不检查本地是否还有没播完的音频。服务端流式合成很快，`response.done` 到达时
本地缓冲通常还剩数秒音频。此时第二条通知被放行，`PCMBuffer` 溢出时从头部丢弃最旧数据，
听感就是上一句结尾被抹掉。

日志证据：`runtime/voice/voice-events-20261107-34308.jsonl` 中 16:56:10 与 16:56:14
两次 `response.create` 相隔 4 秒，16:56:21 记录 `playback_backlog dropped 13440 bytes`
（约 0.28 秒音频）。

### 修复

1. `_request_audio_response` 增加播放守卫：正在播或有缓冲音频时不发起，标记待续。
2. 待续分支同样要求播放结束。
3. 通知与主动话题分支除了 `not _playing` 再要求 `not _pcm`。
4. `_playback` 不再因为单帧空缓冲就把播放标记翻成空闲，改为静默 180 毫秒才结束；
   网络抖动不再制造"看起来播完了"的假信号。
5. 用户新问题仍然立即打断：`user_text` 分支照旧取消当前回复并清空缓冲。

## 三、按需看一眼：三级阶梯，默认不看

新增 `core/quick_look.py`。它不启动任何定时截屏，只在被调用时看一次，
并按成本从低到高尝试：

| 档位 | 手段 | 实测延迟 | 成本 | 适用 |
|---|---|---|---|---|
| 1 | UIA 结构化控件 | 60-850ms | 免费 | 记事本、浏览器外壳、常规 Win32 程序 |
| 2 | 本机 Windows OCR | 取决于系统组件 | 免费 | 任何窗口，但需已安装识别语言包 |
| 2b | 云端 `qwen-vl-ocr` | 约 1.9-2.9s（大窗口） | 按量 | 本机没装 OCR 时兜底，只读文字 |
| 3 | 云端 `qwen3-vl-plus` | 1-3.6s | 按量 | 需要看懂布局、图标、颜色、图表 |

关键实测：视觉模型的延迟主要来自输出长度，不是看图。同一张图把 `max_tokens`
从 300 降到 40，延迟从 6.4 秒降到约 1 秒。

截图优先用 `PrintWindow` 自绘，被遮挡也能取到内容，不抢前台；全黑时退回屏幕抓取。

### 什么时候看

默认不看。只在四类时机触发：

1. 用户问题的答案只存在于画面里。
2. 用户要点的东西没有系统命令通道。
3. 动作执行后无法确认是否生效。
4. 用户明确要求持续盯着。

### 接入语音

`read_screen` 原先要求屏幕共享已开启，否则直接回"当前共享已停止"。
现改为：没有共享时走 `quick_look` 按需看一眼，不需要用户先开共享。
共享开着时仍优先用实时帧。

`_handoff_request` 不再要求 `screen_context_provider` 与共享处于 active 状态。

### 提示词

`_screen_instructions` 与 `DELEGATE_INSTRUCTIONS` 中"不能要求用户再开启""不能把未就绪
当成没有屏幕能力"这类措辞会迫使模型在空画面上回答"能看见"。已改为：
只有 context 非空且 fresh 才描述画面；读不到就直说"这次没读到"。

## 四、验证

新增测试：
- `tools/test_window_control.py`（8 项）：说法识别、不吞既有浏览器路由、拒绝桌面/自身窗口。
- `tools/test_quick_look.py`（9 项）：控件优先、纯本地不调云端、云端 OCR 兜底、视觉最后、
  拒绝云端时明确失败、读不到不编内容。
- `tools/test_voice_queue.py`（4 项）：连续通知不插队、播完才接、抖动不插队、用户新问题立即打断。

汇总回归 110 项全通过（含原有快速命令、语音控制、响应式语音、共享屏幕、语音助手、桌面访问）。

真实设备侧仍需人工确认：连续两条播报是否还有截断；窗口指令在常用软件上的实际手感。

## 五、边界

- 视觉模型不用于点击窗口边框按钮：坐标误差 20-60 像素，点歪的代价高于收益。
- 本机 OCR 依赖 Windows 识别语言包，本机当前未安装，会自动降级到云端识字。
- 云端视觉按图片计费，`quick_look` 默认不调用，仅在文字不够时使用。
